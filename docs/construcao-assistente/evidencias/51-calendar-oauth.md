# #51 — credencial Calendar durável e consentimento privado

O gateway do produto passa a usar exclusivamente `CALENDAR_OAUTH`, um binding privado para `CalendarOAuth`; o antigo access token estático não é alternativa do produto. Flue/modelo não recebem esse binding, credencial ou transporte. A classe é exportada pelo bundle oficial `assistant/cloudflare.ts`; #56 deve criar a migração DO SQLite e binding próprios. O código local não declara recurso provisionado/homologado.

`CALENDAR_OAUTH_CLIENT_ID`, `CALENDAR_OAUTH_CLIENT_SECRET`, `CALENDAR_OAUTH_REFRESH_TOKEN` inicial e `CALENDAR_OAUTH_ENCRYPTION_KEY` são secrets do Worker. `CALENDAR_OAUTH_CONFIGURATION_VERSION` e `CALENDAR_OAUTH_SECRET_EPOCH` fixam configuração operacional. `CALENDAR_OAUTH_CREDENTIAL_GENERATION` é pinada no provisionamento privado; uma geração restaurada diferente recusa antes de bootstrap. Restore55 não deve atualizar esse marker automaticamente nem apagar o DO anterior. O nome DO usa instalação/geração/versão/epoch; o receiver verifica afinidade e seu id nominal, recusando outro DO antes de storage/rede. Cache e eventual refresh token rotacionado ficam cifrados AES-GCM somente no DO, com AAD vinculada também ao clientId; nada disso vai ao D1, MCP ou Git.

O controlador persiste attempting antes do único POST fixo para `https://oauth2.googleapis.com/token`. Valida Bearer, expiração conservadora e scopes exclusivamente calendar.events.readonly/calendar.readonly; outro escopo não passa. Cache durável sobrevive a reinício. Omitir refresh_token conserva o anterior; um token novo é cifrado e confirmado antes de liberar o access token ao host. ACK perdido do commit recupera exatamente o mesmo estado, sem outro POST. Restart/timeout/resultado não comprovado conserva uncertain e não repete automaticamente. Somente HTTP400 válido com invalid_grant pode publicar needs_consent. Estado malformado, chave errada ou contexto diferente falham fechados sem rebootstrap sobre credenciais existentes.

SourceAccess autoriza todos os suportes canônicos ANTES de pedir token; um novo batch confirma as permissões depois do refresh e antes do primeiro GET Calendar. O batch final continua obrigatório após as respostas. O único POST pertence à autorização OAuth; o transporte Calendar continua GET-only. Secrets/credenciais não são retornados por erro e o DO nega fetch público.

## Configuração e consentimento

Criar um client Google próprio do produto e habilitar Calendar API. O consentimento precisa conceder acesso offline para permitir refresh; códigos são trocados no endpoint de token e as credenciais devem ser mantidas em armazenamento privado durável. [Google: fluxo web server](https://developers.google.com/identity/protocols/oauth2/web-server).

`node scripts/calendar-oauth.mjs --help` descreve o mecanismo sem imprimir secrets. O script recebe clientId/clientSecret e OPERATIONAL_GENERATION somente pelo ambiente privado, gera state+PKCE, abre callback em127.0.0.1:8977 e exibe apenas a URL de consentimento. Registrar exatamente `http://localhost:8977/callback`. Na VPS, o dono usa o navegador com encaminhamento SSH `-L 8977:127.0.0.1:8977`; não é necessário computer use na VPS. O callback valida origem/caminho, state/code únicos e consumo único; não reflete query nem chama recursos externos na página. O processo troca o código uma vez e salva refresh token/chave em arquivo0600 fora do Git, sem imprimir tokens, sem guardar access token e sem sobrescrever arquivo existente. O executor provisiona os secrets no Worker por canal privado. A observação da conta Google ou um conector desta conversa não substituem esse consentimento.

No Google, app externo em Testing recebe refresh token com validade de7dias para esses scopes; planejar configuração adequada ou nova autorização explícita durante um piloto mais longo, sem prometer continuidade de14dias por um teste sintético. [Google: expiração de refresh tokens](https://developers.google.com/identity/protocols/oauth2#expiration).

Epoch/configuração novos NÃO são retry de um refresh incerto. Uma substituição exige nova configuração/consentimento explícito e preservação do DO anterior com sua tentativa incerta. Trocar clientId/chave sem o epoch correspondente falha fechada; não existe promessa de rotação transparente. A chave de cifra deve permanecer privada e recuperável junto à configuração; perder a chave impede usar o cache antigo.

## Verificação controlada

Testes dirigidos cobrem cache/expiry/restart, refresh rotacionado, concorrência, attempting, rollback, ACK perdido na admissão/commit, scopes indevidos/ausentes, expiração inválida, invalid_grant, erro/redirect, ciphertext/AAD, DO nominal e revogação durante refresh. O script tem checks Node sem rede para PKCE/state, rejeição de callback, scopes, arquivo0600 e no-overwrite. Suíte D1/workerd final:53/53 em3 arquivos (OAuth19, Calendar22, GitHub12),15,73s. Checks Node do consentimento:3/3,121ms; `npm run check` verde. Os testes não usam Google real. As duas contraprovas do wrapper não usam ctx falso: workerd recusa esse construtor, por isso foram movidas para `scripts/calendar-oauth-runtime.check.mjs`, que exercita DO SQLite real; execução nativa ainda aguarda janela coordenada.

Revisão adversarial independente identificou o risco de múltiplos DO IDs e o contorno de uncertain por restore de geração. Guard nominal e marker de geração foram incorporados, junto à retirada do fallback estático de produto. Não foram encontrados outros bloqueantes no código, condicionado aos testes e à integração; isso não substitui homologação cloud/Google.

Nenhuma API de Google real, inferência paga, WhatsApp ou escrita de agenda chamada nesta implementação. Orçamento/recibos anteriores intactos. Consentimento/configuração Google, deploy e homologação cloud/cliente continuam pendentes e separados do código sintético.
